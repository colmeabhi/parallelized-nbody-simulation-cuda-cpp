Bug fix

The race in the original kernel

The first version computed forces and updated positions in one kernel. CUDA runs blocks in no fixed order, so block 0 could overwrite pos[] while block 7 was still reading it. Some bodies felt their neighbours at time t, others at t + dt, and results depended on scheduling. The fix splits the step so that no kernel reads an array that the same kernel writes.

block 0
read pos[ ]write pos[0..255]
block 7
read pos[ ] … stale or new?write

Block 7's reads overlap block 0's writes. Nothing in the kernel orders them.

After · two kernels per step
kernel 1
v += a·dt/2 ; x += v·dt (own body only)
launch boundary = grid-wide barrier
kernel 2
a = F(x) reads all x ; v += a·dt/2

Positions change only in kernel 1. Every block finishes before kernel 2 reads them.

Integrator

Euler was posing as leapfrog

The old update v += a·dt; x += v·dt is semi-implicit Euler: symplectic, but first order. It is now a real kick-drift-kick leapfrog, which is second order and time-reversible and still costs one force evaluation per step, because the acceleration at the end of a step is reused at the start of the next.

Semi-implicit Euler

vn+1 = vn + a(xn)·dt
xn+1 = xn + vn+1·dt

Spring a = −x, dt = 0.1, from x = 1: x₁ = 0.99000 (error 5·10⁻³)

Kick-drift-kick leapfrog

v½ = vn + a(xn)·dt/2
xn+1 = xn + v½·dt
vn+1 = v½ + a(xn+1)·dt/2

Same spring: x₁ = 0.99500 vs exact cos 0.1 = 0.99500 (error 5·10⁻⁶)

N = 1024, 20 time units. At dt = 0.01 both schemes drift by percents. Bulge stars passing the softened black hole orbit on a timescale √(ε³/MBH) ≈ 0.013, about one step. Once dt resolves that, KDK's error falls about 7× per halving and Euler's about 2×.

Algorithm

When does Barnes–Hut beat brute force?

An octree groups distant stars into one pseudo-mass (opening angle θ = 0.5), turning O(N²) into O(N log N) for about 1 % force error. Each body costs much more than one vectorised direct interaction, so the tree only wins past a crossover.
